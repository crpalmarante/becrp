---

# 1. Objective

This RFC defines the event model for the **Receiving** domain.

The Receiving Event Model establishes the standard events published and consumed by the Receiving module.

Its purpose is to enable loose coupling between business domains through an event-driven architecture.

---

# 2. Motivation

Receiving interacts with several independent domains.

Examples include:

- XML Monitor
- Product Localization
- Supplier Update
- Physical Verification
- Inventory
- Fiscal
- Finance

Direct dependencies between these modules increase complexity.

Domain events allow every module to evolve independently while preserving business consistency.

---

# 3. Principles

The Receiving Event Model follows these principles:

- Events represent business facts.
- Events are immutable.
- Events describe completed business actions.
- Events never expose implementation details.
- Events may have multiple consumers.
- Publishers never know who consumes the event.

---

# 4. Event Structure

Every event follows a common structure.

```text
Event

----------------------------

event_id

event_name

event_version

occurred_at

aggregate_id

aggregate_type

company_id

user_id

payload
```

Events are immutable after publication.

---

# 5. Aggregate

Receiving is the aggregate root.

```
Receiving

↓

Receiving Events
```

Every published event belongs to exactly one Receiving aggregate.

# 7. Event Payload

Example:

```json
{
  "receiving_id": "REC-000001",
  "supplier_id": "SUP-100",
  "warehouse_id": "WH-01",
  "status": "Completed",
  "occurred_at": "2026-08-01T10:15:00Z"
}
```

Payloads should contain only the information required by consumers.

Large objects should never be embedded.

---

# 8. Event Ordering

Events generated by the same Receiving aggregate must preserve publication order.

Example:

```
receiving.created

↓

receiving.validation.completed

↓

physical.verification.completed

↓

receiving.inventory.requested

↓

inventory.processing.completed

↓

receiving.finance.requested

↓

finance.processing.completed

↓

receiving.fiscal.requested

↓

fiscal.processing.completed

↓

receiving.completed
```

Consumers must not assume ordering across different aggregates.

---

# 9. Event Delivery

The platform guarantees:

- At-least-once delivery.
- Durable persistence before publication.
- Event replay support.
- Retry on transient failures.

Consumers must therefore be idempotent.

---

# 10. Event Versioning

Events may evolve.

Every event includes:

```
event_name

event_version
```

Breaking changes require a new version.

Older versions remain supported according to platform compatibility policies.

---

# 11. Event Consumers

Typical consumers include:

Inventory Domain

Processes stock operations.

Finance Domain

Creates financial obligations.

Fiscal Domain

Processes fiscal bookkeeping.

Notification Service

Notifies users.

Audit Service

Stores immutable business history.

Reporting

Builds operational dashboards.

Additional consumers may subscribe without changing the publisher.

---

# 12. Security

Events must never expose:

- passwords;
- authentication tokens;
- confidential credentials;
- encrypted secrets.

Only business information required by consumers may be published.

---

# 13. Audit

Every published event records:

- Event ID
- Publisher
- Timestamp
- Aggregate
- Version
- Payload checksum

Events become part of the permanent business history.

---

# 14. Error Handling

Publication failures must never corrupt the Receiving aggregate.

The platform should support:

- retry;
- dead-letter queue;
- replay;
- monitoring;
- alerting.

# 16. Final Considerations

The Receiving Event Model defines the public business contract of the Receiving domain.

Every interaction with external modules occurs through immutable business events rather than direct dependencies.

This approach improves scalability, simplifies maintenance, enables asynchronous processing and preserves clear domain boundaries.

The event model reinforces the core architectural principle of the Retail Platform:

> **Simple is always better than complex.**
